# Williams AI — полная рыночная история Binance на всех поддерживаемых ТФ

## Что именно уже реализовано

У Williams AI появился **источник реальных публичных OHLCV графиков Binance
USDⓈ-M Futures** с постраничной загрузкой и приватным SQLite-кэшем.

**15 официальных интервалов** Binance:
`1m, 3m, 5m, 15m, 30m, 1h, 2h, 4h, 6h, 8h, 12h, 1d, 3d, 1w, 1M`.

Для каждого инструмента и каждого ТФ сохраняются не только OHLC и базовый
объём, но и quote-volume, число сделок, taker-buy base/quote volume,
`openTime`/`closeTime`, метаданные биржевого источника. Эти значения
могут служить дополнительной наблюдаемой рыночной информацией, но **число
сделок Binance не выдаётся за подлинный книжный tick-volume для Squat**.

При первой загрузке используется несколько запросов
`GET /fapi/v1/klines?symbol=...&interval=...&startTime=...&endTime=...&limit=...`.
Официальный максимум — 1500 баров за вызов; наша реализация
преднамеренно запрашивает **не более 1000**, с ограниченной частотой.
При последующих запусках загружаются только новые закрытые свечи.
Предыдущая свеча перечитывается и проверяется на неизменность.

Все интервалы строятся **из своих настоящих биржевых свечей**.
Недопустимо выдавать 500 часов H1 за полноценную историю D1 либо
искусственно восстанавливать M1 из H1.

Волновой анализ выполняет `chart_reader.analyze_chart` на каждом из
15 ТФ отдельно. Сохраняются подтверждённые экстремумы, структура,
контекст Alligator/AO/AC, кандидаты WM1/WM2/WM3, условные коррекции,
импульсные альтернативы и признаки TC1. Старшие и младшие масштабы
сопоставляются как **конкурирующие сценарии**, но не как окончательно
подтверждённая волновая разметка. Принцип «~100–140 баров на волну»
используется только как ориентир масштаба, не железное правило.

Локальная GGUF Qwen дополнительно получает компактную информацию о
доступных ТФ, **только когда свечи каждого из этих ТФ уже были закрыты
к моменту рассматриваемого H1**. Модель объясняет предположения,
независимый критик проверяет книжные утверждения; **заявки отключены**.

## ВАЖНО: источники DEMO и публичного фьючерсного рынка различаются

- `PUBLIC_USDM` → `https://fapi.binance.com`:
  реальная **публичная** история фьючерсных цен для обучения, без
  логина, торговых API-ключей, передачи приватных данных и ордеров.
  Использование публичного market data **не означает** production-trading.
- `DEMO_USDM` → `https://demo-fapi.binance.com`:
  публичная история доступной тестовой торговой среды, без ключей.
  Доступная глубина Demo может отличаться от производственного рынка.
- **Система никогда не подменяет один источник другим автоматически.**
  В SQLite они хранятся с независимыми venue-идентификаторами.
- Некоторые географические/серверные среды, включая проверенный
  GitHub Actions runner, возвращают Binance **HTTP 451**. Такая попытка
  заканчивается ошибкой, не создавая фальшивых графиков. Сборка/тесты
  в GitHub не доказывают, что полная история уже скачана.

## Настройка на устройстве/компьютере с разрешённым доступом

Нужен Python 3.11 из новой ветки Williams-AI и существующий **приватный**
каталог (пример `/private`). Веса модели не обязательны для первого шага.
Никакие API-ключи Binance не нужны.

**Первая загрузка ETHUSDT на ВСЕХ 15 временных интервалах:**

```bash
python -m williams_ai.binance_wave_study sync \
  --venue PUBLIC_USDM \
  --db /private/binance_usdm_wave_history.sqlite3 \
  --symbols ETHUSDT \
  --intervals all \
  --since earliest \
  --max-pages-per-interval 100 \
  --page-size 1000
```

Параметр `--max-pages-per-interval 100` означает максимум 100 тыс.
свечей **для одного ТФ на этот запуск**, не «полную историю» 1m.
Повторять команду с тем же путём к SQLite и тем же `--since earliest`
для безопасного продолжения до состояния `AT_LATEST_CLOSED_BAR`
каждого ТФ. При большой глубине 1m нужно много страниц и дискового места.
Если запрошенная глубина старше фактической Binance listing/public
retention, код сохраняет старейшую реально возвращённую свечу,
**но не заявляет гарантированную полноту с момента листинга**.

**Изучение уже сохранённой истории отдельно, без сетевых запросов:**

```bash
python -m williams_ai.binance_wave_study study \
  --venue PUBLIC_USDM \
  --db /private/binance_usdm_wave_history.sqlite3 \
  --symbols ETHUSDT \
  --intervals all \
  --window 1400 --edition TC2
```

**Дополнение новых свечей и немедленное изучение рынка:**

```bash
python -m williams_ai.binance_wave_study sync-study \
  --venue PUBLIC_USDM \
  --db /private/binance_usdm_wave_history.sqlite3 \
  --symbols BTCUSDT ETHUSDT SOLUSDT XRPUSDT \
  --intervals all --since earliest \
  --max-pages-per-interval 25
```

**Анализ настоящей Qwen (никаких торговых полномочий):**

```bash
python -m williams_ai.binance_wave_study sync-study \
  --venue PUBLIC_USDM \
  --db /private/binance_usdm_wave_history.sqlite3 \
  --symbols ETHUSDT --intervals all \
  --since earliest --max-pages-per-interval 50 \
  --edition TC2 \
  --model /private/Qwen3-1.7B-Q4_K_M.gguf \
  --expected-sha256 <EXACT_REAL_MODEL_SHA256>
```

Для DEMO заменить только `--venue DEMO_USDM`. Не подставлять
ключи Binance, access token или cookie в эти команды.

## Изоляция и поведение при неисправностях

- Только HTTPS GET `/fapi/v1/time`, `/fapi/v1/exchangeInfo`,
  `/fapi/v1/klines`. Нет торгового REST, WebSocket с ключами, ордеров.
- Пропуски, несогласованность календаря 1w/1M, изменение уже закрытой
  исторической свечи или неверные OHLCV **блокируют обновление**.
  Кэш не изменяется частично внутри одной страницы.
- Если данных недостаточно для 45 индикаторных свечей, ТФ получает
  `INSUFFICIENT_HISTORY`, вместо выдуманных волн.
- Незакрытая свеча никогда не попадает в длительный кэш, анализ и GGUF.
- SQLite допускает многократный запуск, сохраняет закрытую историю
  после перезапуска; более раннюю начальную дату для уже начатого потока
  запрещено тихо подменять — нужен отдельный новый приватный файл БД.
- Тот факт, что последние свечи догружены, не доказывает ни полноту
  архивов Binance за весь срок жизни инструмента, ни правильность
  Эллиотт-разметки/финансовых результатов.
- Скачивание и анализ инициируются локальной Python-командой. Это
  **ещё не автоматическая фоновая служба Android**: отдельное мобильное
  подключение, автономный lifecycle и телефонная приёмка не завершены.
- Research-кэш не может включить `demo_pilot_cli`, не имеет доступа к
  DEMO account API и не открывает сделки в любой среде.

## Проверка

CI выполняет синтетические детерминированные отрицательные тесты
всем 15 календарным интервалам, повторной загрузке, загрязнению будущими
свечами, неизменности истории, блокировкам HTTP 451, изоляции
публичного Futures и DEMO, закрытым волновым контекстам и запрету
исполнения. Поскольку GitHub runner имеет Binance API HTTP 451,
здесь пока **нет подтверждения реальной полноглубинной загрузки
15 источников с Binance**. Для такой приёмки нужна сеть с доступом
и конечный экземпляр Python/Android.


## Фактическая внешняя проверка 24 октября 2026

Отдельно от заблокированного GitHub runner я вызвал официальные
read-only Binance USDⓈ-M Futures market-data методы через публичную
интеграцию Binance для **ETHUSDT** по **каждому из 15 интервалов**.
Все 15 запросов вернули реальные 12-польные свечи (по 3 на интервал),
включая 1m, 3d, 1w и 1M; никаких подписанных аккаунтных вызовов
или ордеров не было.

Установлено реальное отличие календаря Binance **3d** от наивной
UTC-эпохи: начало 3-дневной свечи ETHUSDT 23.10.2026 00:00 UTC
(1792713600000 мс) требует смещения якоря на +1 сутки.
Соответствующее исправление добавлено в парсер и закреплено регрессией.
Это подтверждает формат и наличие текущего рыночного потока,
**но не заменяет реальную полноглубинную загрузку и долговременное
хранение на пользовательском устройстве**.


## Автоматическое пополнение графиков при работающем Python-движке

Для автономного получения **публичных свечей** без повторных ручных команд
есть явный foreground-процесс (это не облачный фоновый ChatGPT и пока не
Android foreground service):

```bash
python -m williams_ai.binance_wave_watch \
 --venue PUBLIC_USDM \
 --db /private/binance_usdm_wave_history.sqlite3 \
 --symbols BTCUSDT ETHUSDT SOLUSDT XRPUSDT \
 --intervals all \
 --pages-per-timeframe 50 \
 --poll-seconds 3600 \
 --max-cycles 0
```

`--max-cycles 0` означает работать **пока процесс запущен**,
`Ctrl+C` останавливает. Каждая итерация дозагружает только новые
закрытые свечи после сохранённого checkpoint, проверяет пригодность
каждого ТФ для анализа волн и публикует статус. HTTP451, нестабильная
сеть, нестыковка цены или истории → состояние
`FAILED_UNVERIFIED_DATA`, а не ложное `READY`. Нет ни одной
возможности отправки торговых ордеров или чтения API-ключей.

Если процесс не запущен, автоматическая загрузка не происходит.
Для самостоятельной работы после перезагрузки смартфона необходима
отдельная Android-служба с приёмкой жизненного цикла, пока не созданная.
